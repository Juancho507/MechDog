Introducción al Proyecto

MechDog es un robot cuadrúpedo autónomo desarrollado sobre ROS Noetic con simulación en Gazebo y visualizacion web via noVNC. El objetivo principal es la navegacion autónoma en entornos con obstáculos utilizando exclusivamente un sensor ultrasónico. Este informe compara dos algoritmos clásicos de búsqueda de caminos: A* (A-Star) y BFS (Breadth-First Search) aplicados a la navegación del robot en tres escenarios de dificultad creciente con objetos dispersos.

Arquitectura del sistema:
  • Docker multi-stage (base → builder → visualizer)
  • noVNC para visualización web en http://localhost:6080/vnc.html
  • Gazebo Classic para simulación 3D
  • Navigation stack: A*/BFS + DWA + Occupancy Grid + Safe Learning

Objetivos y restricciones

Objetivos

  • Implementar un sistema de exploración autónoma para el robot MechDog.
  • Desarrollar e implementar dos algoritmos de planificación de rutas (A* y BFS).
  • Crear un entorno de simulación 3D con PyBullet, Docker y noVNC.
  • Comparar el rendimiento de ambos algoritmos bajo diferentes condiciones.
  • Generar un módulo de código independiente para el robot físico.
  • Integrar ROS para escalabilidad futura.

Restricciones

  • Sensores: Solo ultrasónico (no cámara, no LiDAR)
  • Comunicación: solo Bluetooth
  • Robot físico: MechDog Standard Kit de Hiwonder
  • Simulación: debe funcionar en contenedor Docker con noVNC
  • Código del robot: debe ser compatible con Hiwonder Python Editor

Sobre el MechDog

El MechDog es un robot cuadrupedo disenado para educacion e investigacion en robotica. Esta construido con estructura metalica y servo-motores de alto torque que permiten una locomocion versatil.

Locomoción

Utiliza 8 servos (2 por pata) para realizar diferentes tipos de marcha: trote, caminata, giros y posturas estaticas. Cada servo tiene un rango de 0-180 grados controlado via bus I2C con un controlador PWM. La locomoción se basa en secuencias de angulos predefinidas para cada gait.

Sensor Ultrasonico HC-SR04

El robot utiliza un sensor ultrasonico montado en el frente para detección de obstaculos. El sensor emite pulsos ultrasonicos y mide el tiempo de retorno del eco para calcular distancia. Rango efectivo: 2-200 cm, precision de ±3 mm.

Bluetooth

La comunicación inalámbrica se realiza via Bluetooth, permitiendo enviar comandos y recibir telemetria del robot. Protocolo: UART a 115200 baudios.

Programación

El robot es programable mediante "Hiwonder Python Editor", un entorno basado en Python 3 que permite control directo de servos, lectura de sensores y comunicación Bluetooth. El SDK oficial incluye bibliotecas para control de movimiento.

Limitaciones

  • Sin cámara.
  • Sin LiDAR ni sensores de profundidad.
  • Rango limitado del sensor ultrasonico (2m max).
  • Campo de visión estrecho (cono de ~15 grados).
  • Batería limitada (~30 min de operacion continua).
  • Sin odometría precisa (sin encoders en servos básicos).

Sobre ROS

¿Qué es ROS?

Robot Operating System o más conocido por sus siglas "ROS", es un framework de middleware utilizado para el desarrollo de software roboticio. Este proporciona servicios de comunicación entre procesos (nodos), abstraccion de hardware, herramientas de visualización y una amplia comunidad de paquetes reutilizables.

¿Por qué se usó ROS?

Después de una ardua investigación, estas fueron las 5 características que más destacaron del sistema y lo que llevo a nuestra decisión final de usarlo.

  • Modularidad: Separa la navegación, mapeo y control en nodos independientes
  • Escalabilidad: Permite anadir nuevos sensores y algoritmos sin reescribir el sistema
  • Comunicacion: Topics, servicios y acciones para intercambio de datos
  • Simulacion y realidad: El mismo código ROS funciona en simulación y en el robot físico
  • Herramientas: rviz, rqt, rosbag para depuración y análisis

Algoritmos Implementados

Dado el análisis anterior se decide implementar 2 algoritmos, los cuales son:

A* (A-Star)

Tipo: Búsqueda informada (heurística).

Principio: Combina el costo real del camino recorrido (g(n)) con una estimación heurística del costo restante (h(n)) para guiar la búsqueda hacia la meta. Utiliza una cola de prioridad (min-heap) para explorar primero los nodos mas prometedores.

f(n) = g(n) + w · h(n)

Dónde w es el peso heurístico (configurable, tipicamente 1.0) que controla el balance entre optimalidad y velocidad.

Heurísticas disponibles:

  • Manhattan: Apropiada para movimiento en cuadricula con restriccion 4-conectada.
    h(n) = |x₁ - x₂| + |y₁ - y₂|
  • Euclidea: Apropiada para movimiento libre en cualquier direccion.
    h(n) = √((x₁ - x₂)² + (y₁ - y₂)²)

Características:

  • Encuentra el camino óptimo si la heurística es admisible (no sobrestima).
  • Más rápido que BFS porque dirige la búsqueda hacia la meta.
  • Menor consumo de memoria que BFS.
  • Puede no encontrar solución si la heurística sobreestima el costo.

Complejidad:

  • Tiempo: O(b^d) en el peor caso, pero típicamente mucho menor con buena heurística
  • Espacio: O(b^d) almacena todos los nodos generados

BFS (Breadth-First Search)

Tipo: Búsqueda no informada (ciega).

Principio: Explora el grafo por niveles, expandiendo primero todos los nodos vecinos antes de pasar al siguiente nivel. Utiliza una cola FIFO (First-In-First-Out) para asegurar que se exploran primero los nodos más cercanos al origen.

Características:

  • Garantiza encontrar la solución de menor longitud en número de pasos.
  • Siempre encuentra una solución si existe.
  • Puede ser muy lento en mapas grandes (explora en todas direcciones).
  • Alto consumo de memoria (almacena todos los nodos del nivel actual).

Complejidad O(b^d):

  • Tiempo: Expande todos los nodos hasta profundidad d.
  • Espacio: Almacena todos los nodos del nivel actual.

Pero... ¿Por qué solo A* y BFS?

Para este proyecto se seleccionaron exclusivamente estos dos algoritmos por las siguientes razones técnicas y prácticas:

Algoritmo ¿Por qué NO se incluyo?
DFS (Depth-First Search) No garantiza caminos óptimos. Puede ciclar infinitamente. No adecuado para navegación real donde cada movimiento tiene costo.
Greedy / Hill Climbing Se queda atascado en mínimos locales. No garantiza encontrar solución. Inseguro para robot real.
Q-Learning Requiere cientos de miles de episodios de entrenamiento. Inviable con un solo sensor ultrasonico y sin GPU. El robot real (ESP32) no tiene capacidad para entrenar.
PPO / DQN / RL Requieren redes neuronales, GPU y grandes volumenes de datos de entrenamiento. Totalmente inviables en ESP32. El riesgo de colisiones durante entrenamiento viola el principio de Safe Learning.
Algoritmos Genéticos Requieren evaluar cientos/miles de generaciones. Computacionalmente costosos. No adecuados para navegación en tiempo real.
Dijkstra Equivalente a A* con heurística h(n)=0. A* subsumee a Dijkstra y es más eficiente.
Decisión de diseño: A* y BFS son determinísticos, predecibles y garantizan solución. Esto es crítico para Safe Learning, no se puede permitir colisiones durante la fase de exploración y aprendizaje. Además, el ESP32 del MechDog real no tiene recursos para redes neuronales ni aprendizaje por refuerzo.

Safe Learning (Aprendizaje Seguro)

El modulo de Safe Learning es un componente crítico que opera en paralelo al planificador para garantizar la integridad fisica del robot. Implementa un sistema de seguridad de tres niveles:

Critico

Distancia < 0.15m

Parada inmediata

Frenado máximo

Warning

Distancia < 0.30m

Reducción de velocidad

Escalado proporcional

Safe

Distancia > 0.30m

Ejecución normal

Sin restricciones

Componentes del Safe Learning:

  • Polígono de seguridad dinámico: Se expande proporcionalmente a la velocidad: largo = base_length + v · linear_factor. A mayor velocidad, mayor área de seguridad al frente.
  • Frenado predictivo: Calcula la distancia de frenado necesaria: d = v²/(2·a) + v·t_reaction y la multiplica por un factor de seguridad (1.5~2.0).
  • Detección de punto muerto (dead-end): Después de 3 paradas de emergencia consecutivas, activa el modo de recuperacion.
  • Home Base / Punto Bueno: Si se excede el máximo de recuperaciones, el robot retorna automáticamente al punto de partida.
  • Filtrado de autocolisiones: Ignora lecturas del sensor por debajo de range_min + 0.06m para evitar que las patas del robot disparen falsos positivos.

Punto Bueno (Home Base)

El Punto Bueno o Home Base es la posición de origen a la que el robot puede retornar si encuentra condiciones inseguras. Implementado en home_base_node.py:

  • Posición inicial: Se establece en las coordenadas de spawn del robot (tipicamente 0,0).
  • Retorno automático: Si se superan N intentos de recuperación consecutivos, se envía automáticamente un goal de retorno al home.
  • Zona segura: Radio de 1.0m alrededor del home donde el robot está a salvo.
  • Visualización: Se publica un marcador verde en RViz para identificar visualmente la posición del home.

Escenarios de Prueba

A diferencia de un laberinto tradicional (con pasillos y paredes), los escenarios diseñados son campos abiertos con obstáculos dispersos que el robot debe analizar y rodear para encontrar la mejor ruta hacia la meta.

Simple

3 obstáculos

Para validación básica del sistema. Obstáculos separados con espacio suficiente para maniobrar.

Medium

8 obstáculos

Dificultad media. Obstáculos colocados en patrones que requieren desviaciones de la línea recta.

Complex

15 obstáculos

Alta densidad de obstáculos. El robot debe calcular rutas complejas con múltiples cambios de dirección.

Conclusiones

Veredicto Final

Ejecuta experimentos para determinar el ganador entre A* y BFS.

Recomendaciones:

  • A* es la opción recomendada para el MechDog real por su eficiencia computacional y menor memoria requerida.
  • Safe Learning es indispensable sin el módulo de seguridad, cualquier planificador puede generar rutas que resulten en colisiones.
  • El Punto Bueno (Home Base) proporciona una red de seguridad adicional permitiendo retirada automática ante fallos.
  • Para el robot fisico con ESP32, se recomienda A* con heurística Manhattan y peso 1.0 como configuración base.
